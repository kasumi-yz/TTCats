# 写实片段用 VP9 透明 WebM 存储，所有片段的首尾都必须是某个姿势

第一、二阶段是写实风格，所有动画都由 AI 视频生成。

**存储格式**：运行时，片段存成带透明通道的 VP9 WebM，由 PixiJS 当作视频纹理来渲染。不存成一帧帧的图片，是因为写实动画需要 24fps，图片序列会占用太多内存。

**姿势规则**：为了让任意两个片段都能无缝衔接，每个片段都必须从某个姿势开始、在某个姿势结束。

- 基础姿势：站、坐、睡
- 连接姿势：悬空、伏低、腾空

生成片段时，用 AI 工具的首尾帧功能，把对应的姿势帧设为首帧和尾帧。

## Consequences

- 片段被打断时怎么衔接，M0-A 用合成片段实测后暂定为：平常的姿势变化，等回到姿势后播过渡片段；用户触发的打断（拎起、点击）立刻硬切，加小特效遮挡；交叉淡化只用在前后画面很像的时候。用豆豆的真实片段复测后定稿。
- 拎起不能等片段回到姿势，必须立刻切。"任意姿势 → 悬空"从片段中间切进去能不能接受，要用真实片段确认；不能接受就用硬切加特效。
- 每只猫只预加载"正在播的"和"接下来要播的"片段（M0-A：比全部预加载省约 90MB，打断反应只慢约 15ms）。
- 备选方案（把短循环片段预先解码成一帧帧图片）M0-A 算过内存，比视频纹理更大，不采用。
- 猫的外观不能随需求变化，也没法"穿戴"东西。装扮类玩法改为摆放家具。
- M0-A 已用合成片段验证：PixiJS 视频纹理播放 VP9 透明 WebM，透明边缘正常；三只猫同时播放，在核显、限 30fps、按需加载片段的条件下，整机 CPU 平均 1.7%，在 2% 的目标以内，峰值 2.0% 已经碰线；不限帧率时约 3.2%，超标，所以正式程序必须用核显并限 30fps；`requestVideoFrameCallback` 能准确拿到当前帧号，用来查点击遮罩。详见 `docs/验证报告/M0-A-渲染与交互.md`。
- 还要用豆豆的真实片段复测：一整条动作链的衔接效果、毛边在深色和浅色壁纸上的效果。复测通过后改成 accepted。
