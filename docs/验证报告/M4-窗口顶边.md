## 实现与边界

- `app/src/main/platform/win/windows.ts`：调用时才加载 DLL；查询线程临时使用 Per-Monitor V2，结束后恢复原上下文。主进程自己的窗口默认完全排除。窗口快照包含物理边界、DPI 感知方式、最小化/最大化/全屏/系统隐藏状态、按钮来源，以及是否可以站立、是否参与遮挡。窗口标题不采集。
- Z 序使用 `GetTopWindow`、`GetWindow(GW_HWNDNEXT)`；与 `EnumWindows` 的句柄快照对照，不假设回调顺序。遇到环或缺少仍存在的窗口最多重试三次，之后明确报错。[Windows 对 GetWindow 的 Z 序及循环风险说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindow)。
- 不支持 DPI 或只感知系统 DPI 的程序优先使用 `WM_GETTITLEBARINFOEX` 的屏幕坐标，不沿用 M0 对 DWM 偏移与宽高一起放大的公式。消息有 8 ms 超时；取得的矩形不夹边，明显不在窗口外框内则拒绝作为按钮。随后同样尝试系统命中边界校正；无法可靠定位按钮时不提供可站顶边。[TITLEBARINFOEX 的坐标和按钮索引](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-titlebarinfoex)。辅助功能或命中接口不能替代实际图像的独立视觉核对。
- Per-Monitor 窗口同样优先使用标题栏绝对坐标。第五轮确认 WinUI 记事本的 DWM 区域左端多留空白，所以不把它当首选；标题栏接口无有效数据时才读取 DWM 相对按钮坐标并加物理外框原点。自绘标题栏两种来源都无效时保守预留右侧 160 DIP，并标记 `fallback`。这些退路没有通用准确性保证，核对脚本仍要求与实际按钮一致。[DWM 对按钮边界的定义](https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute)。
- 第六轮发现浏览器自绘按钮与标准标题栏尺寸不同。窗口以标题栏/DWM 作为定位提示，通过 `WM_NCHITTEST` 二分实际按钮联合边界，标记 `hit-test`；审查后的独立 Legacy 预检证明 DPI 不感知窗口也需要这一步，已取消只对 Per-Monitor 校正的限制。超时立即停止继续发送消息，布局不能定位时保留原来源及其已声明限制。相对矩形缓存最多 1 秒；移动只平移，尺寸、DPI、进程及提示布局改变时重读，不可站立/关闭时清理缓存。同尺寸动态布局最多等待 1 秒重新校正。算法假定相邻标题栏按钮构成连续联合矩形，非标准离散形状不保证精确。[系统命中返回值](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-nchittest)。
- 工具窗口、太小窗口、最大化或全屏窗口不站猫，但有实体时仍遮挡下层。沿用已测试的 M0 策略：分层且鼠标穿透的窗口、全局 alpha 为零的窗口不参与遮挡。逐像素透明、可见的穿透装饰和圆角仍不作精确形状判断，按 M0 的限制记录，不能宣称通用透明遮挡已解决。
- `window-ledges/compute.ts`：纯计算，不依赖 Electron 或系统；使用猫所在屏幕的**物理工作区**及缩放，按 #106 的 `LedgeWindow` 输出局部 CSS 坐标。每个窗口的完整 `left/right/top` 不裁剪，只有可站 `segments` 裁到工作区、扣除按钮与上层遮挡；横向完全在屏幕外或完全被挡时保留空段，其他屏幕的窗口不会提供可站段。这样窗口部分移出屏幕后继续移动，真实边界和速度不会被夹边吞掉。默认排除短于 8 DIP 的碎线；猫的宽度、身体上方空间和落脚条件归 #115。
- `window-ledges/tracker.ts`：地板模式无定时器、无系统读取；窗口模式空闲时设定 1000 ms 延时，有猫站顶边时设定 33 ms 延时。实际间隔包含查询耗时及调度延迟，**33 ms 不是实测间隔或延迟保证**。本次决定保留这一采样方案，在下一轮同时记录回调实际间隔和移动延迟，不在测后为更换计时方式额外要求重测。Claude 在 Zephyr 只读测得 `setTimeout(33)` 平均约 46 ms、约每秒 21 次，详见[审查记录](https://github.com/kasumi-yz/TTCats/pull/126#issuecomment-5970130812)；这是审查者测得的计时器间隔，不是当前模块或猫呈现的验收数据。输出位移、实际采样间隔和不可站立通知；查询失败清掉旧顶边并报告错误，下一轮重试。`refresh()` 供 #116 的屏幕变化和调试触发使用。

## 真机核对方法

从工作树的 `app/` 运行：

```powershell
# 只读环境和窗口信息，不移动、不测性能；可直接运行。
npx electron scripts/verify-window-ledges-entry.js --inspect

# 只读预检：不独占、不移动用户窗口、不取桌面图像、不测 CPU、不动鼠标。
# 两个独立 Legacy 窗口在所有屏幕之外创建，验证按钮与置顶排序后关闭。
npx electron scripts/verify-window-ledges-entry.js --preflight --legacy=<窗口句柄>

# 预检和自动检查全通过后，笔记本取得一次明确批准，完整核对所有项目。
npx electron scripts/verify-window-ledges-entry.js --approved --measure --legacy=<窗口句柄>

# 台式机两种配置取得一次批准；从 3440×1440 100% 开始。
# 脚本保存第一份结果后提示切换为 2560×1440 100%，用户完成后输入回车继续。
npx electron scripts/verify-window-ledges-entry.js --approved --desktop-batch --legacy=<窗口句柄>

```

脚本要求记事本、实际浏览器、资源管理器和一个 DPI 不感知老程序的窗口存在；缺少任何一个都会记录失败。浏览器同时核对进程名称，避免误选同样使用 Chromium 窗口类的 Codex，优先选普通显示的窗口。另在独立进程创建真正的 DPI 不感知 Legacy 标准窗口，以及遮挡窗口和两种透明层，Legacy 不冒充真实老程序应用。测试暂时移动、调整大小、最小化和最大化窗口，结束后恢复原位置、大小及状态；只关闭本轮创建的测试窗口，不关闭用户应用；不操作鼠标。不支持的最小化/最大化明确记录为不适用。

`verify-window-caption.ps1` 在单独的 PowerShell 进程中通过 UI Automation 获取按钮，按公开名称及 AutomationId 识别，不输入被测算法的边界。保留所有失败原文、WindowPattern 能力和元素 FrameworkId。原生预测矩形的**左边、右边和宽度**必须分别相符，误差仍为 2 物理像素；上下差异只记录，因为顶边计算只使用按钮左右范围。旧算法的 335 像素过大预留仍会失败。正式二分和核对用逐像素扫描不共享实现，但都依赖系统命中接口，不能声称来源独立。

辅助功能核对同时读取窗口树及右上角实际屏幕位置的元素；统一 Per-Monitor V2 物理坐标，排除其他进程、标签页关闭按钮并按矩形去重。第九轮资源管理器通过这条路径取得真实按钮，没有触发鼠标悬停，因此移除了未使用的悬停备选。

所有应用都必须保存实际按钮图像，包括取得 UIA 参考的应用。只有 Per-Monitor 且窗口 DPI 与所在显示器 DPI 相同，才使用 `PrintWindow`；其他窗口一开始就用物理屏幕截图。整个窗口仅存在内存，磁盘只保存按钮区域及 16 DIP 横向上下文，不保存标题和正文，不经过 Electron 缩略图缩放。[PrintWindow 说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)。截图方式、文件名、纯色/尺寸错误都记录，逐张视觉核对后才能宣称实际按钮通过；UIA 和命中扫描都无有效参考时也明确失败。

第九轮 IExpress 的纯色有明确 DPI 根因：审查者在屏幕外复现了 900×600 的物理位图只绘入左上 600×400 的逻辑内容，右上按钮区落在未绘制处；跨过分界的错位图像甚至可能不是纯色，所以不能先试 `PrintWindow` 再凭纯色决定换来源。[复现数据与审查](https://github.com/kasumi-yz/TTCats/pull/126#issuecomment-5970130812)。本次直接选屏幕截图，临时置顶后在截取区域四角和中心检查所属窗口；被遮挡或纯色仍失败。预检只校验路径选择，不把它说成已取得有效屏幕图像。

资源管理器的 UIA 元素 FrameworkId 为空、根元素为 Win32，这不能证明提供者究竟使用哪个接口。.NET 的标准标题栏代理源码中，按钮 BoundingRectangle 调用 `Misc.GetTitlebarRects`，其 Vista 以后路径调用 `WM_GETTITLEBARINFOEX`，因此可能与正式来源相同，不能仅凭坐标相等称为独立验证。[WindowsTitleBar 源码](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/UIAutomation/UIAutomationClientSideProviders/MS/Internal/AutomationProxies/WindowsTitleBar.cs)、[Misc 源码](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/UIAutomation/UIAutomationClientSideProviders/MS/Internal/AutomationProxies/Misc.cs)。本次完整轮次必须为资源管理器补实际按钮图像，作为独立视觉证据。

下一轮采样方案已定：每个应用移动 20 次；命令前用单调时钟登记开始时刻，在 tracker 的 `onUpdate` 到达时直接取结束时刻，要求同一窗口发生横向位移，不轮询发现更新。每次等待下一次移动的设定为 80 ms，回调超时为 500 ms；同时保存所有实际更新间隔和失败样本。它包含系统查询及调度耗时，不包含 IPC 或屏幕呈现，不能证明猫跟随无明显滞后。保留定时采样，不使用事件钩子或新增高精度计时依赖。共享 `Ledges.at` 为读取时的 Unix 毫秒，内部回调测量另用单调时钟，二者不混用。新增真实窗口连续两次部分移出左边界核对，保留原始边界和可站段快照；猫的跟随及速度阈值由 #115 验证。遮挡同时核对 Z 序、被扣部分和仍存在的顶边。

CPU 放在应用移动和按钮核对之前，地板、窗口空闲、窗口占用各预热 1 秒并测量 30 秒，三个阶段互相独立；应用失败不能使 CPU 被跳过。保留一个可站立标准窗口，统计核对进程累计 CPU，同时记录实际采样间隔和查询错误，列单核及按逻辑处理器归一化的整机百分比，整机平均要求低于 2%。创建和核对不计入测量区间。独占检查失败时明确禁止性能采样并保存失败，不能拿竞争环境的数据验收。数值只代表核对进程，完整应用 CPU 须等 #116 接线后另测。

各项目失败均保存后继续，最后列出每项失败；任何失败使整轮状态为 `failed`、退出码 1，成功才为 `passed`。缺少目标也保留失败项，`completedAppChecks` 列出已处理的应用，是否通过由各项状态判断。异常、窗口恢复和测试进程清理结果都进入 JSON；写盘失败会明确抛出，不能声称保存成功。独占不成立等无法安全继续的前提错误会终止本轮，并记录原因。

结果默认写到忽略的 `app/out/window-ledges/`。可将本次真实的部分结果保存到 `docs/验证报告/M4-窗口顶边-证据/`，但必须标明未完成及失败点，不能替代整轮验收。提交的 JSON 不含用户窗口标题、正文或本机绝对路径；截图只保留逐张确认过的按钮区域。失败不能用上一轮的成功文件替代。
