# M0-B 窗口模式小验证

关联：[#3](https://github.com/kasumi-yz/TTCats/issues/3)。工程：`experiments/window-spike/`。

## 结论与验收状态

已实现可独立运行的 Electron + TypeScript + koffi 验证工程，并保留复现脚本、截图和测量摘要。100%、125%、150% 三种 Windows 系统缩放均完成真实窗口验证，六类常见应用的边界跟随和按钮避让计算通过。当前原型支持继续研究窗口模式；自绘按钮、透明置顶层、混合 DPI 和实际屏幕呈现延迟仍有明确限制。

M0 的原型不接入 `app/`，不修改共享接口、schema 或 ADR。不要依据本报告直接把 M4 窗口模式认定为稳定功能。

## 环境

- 日期：2026-09-30（America/New_York）。
- Windows 内核版本 10.0.26200；机器注册的产品名称为 Windows 10 Home China，不能用该名称推断实际系统大版本。
- AMD Ryzen 9 8945HS，16 个逻辑处理器，约 32 GB 内存。
- 单显示器，2880 × 1800 物理像素，150% 时 Electron 显示范围为 1920 × 1200 逻辑像素，120 Hz。
- Node.js 开发环境 24.15.0；Electron 44.5.1 内含 Node.js 24.21.0 / Chromium 152.0.7977.130；koffi 3.3.2；版本锁定在独立 package-lock.json。
- 性能运行前检查没有其他开发会话的 `electron.exe` 或 Python 素材工厂进程；验证窗口与性能测量分开运行。普通用户应用仍保持运行。

## 自动与真实桌面验证

`npm test`：6 项全部通过，没有跳过。覆盖矩形遮挡与按钮区域、多重 / 完全遮挡、负坐标、下层窗口不遮挡上层窗口，以及 100% / 125% / 150% DPI 下速度阈值一致。

`npm run verify`：100%、125% 下各 10 项检查通过，150% 下修复后的 12 项检查通过：独立进程窗口枚举、遮挡和按钮区域扣除、坐标往返、快速移动、移动到渲染回执的响应、最大化、最小化、隐藏、全屏和恢复；新增画布 CSS 尺寸及频繁换序期间 300 次枚举检查。100% 和 125% 的记录来自修复前，证明真实系统 DPI 的坐标换算，不作为修复后画布尺寸或换序回归的证据。测试窗口从 Win32 读取，真实执行状态切换，不用模拟窗口列表冒充系统验证。

`npm run verify:apps`：在 150% 下依次移动资源管理器、Chrome、微信、VS Code、记事本和设置，各自的物理边界变化均为 `(180,40)`，且按钮区域没有出现在窗口顶边中。测试在 finally 中恢复窗口位置与最大化状态。VS Code 使用官方 ZIP 便携版 1.140.0，数据在已忽略的 `results/vscode/data/`；未安装到系统。Node 测试进程单独设置线程 DPI 感知，避免 `SetWindowPos` 接收虚拟化坐标。结果见 [apps-150.json](M0-B-证据/apps-150.json)。

已有置顶应用会完全遮住测试窗口，所以 `verify` 的几何断言和截图只使用两个测试窗口的真实枚举结果。没有窗口顶边时测试会失败，避免空结果误判通过。普通运行和性能测量使用完整桌面的 Z 序。这一隔离验证不能替代用户桌面的人工观察。

## 跟随延迟与 CPU

目标采样周期是 100 ms。速度使用真实经过时间归一化到逻辑像素/秒；测试窗口每 350 ms 左右移动 120 逻辑像素，快速移动检测通过。阈值暂取 800 逻辑像素/秒，并未据此决定 M4 的最终“晃动后下落”玩法。

30 秒完整桌面运行的测量摘要保存在 [measure-150.json](M0-B-证据/measure-150.json)。277 次读取平均 2.93 ms，P95 3.58 ms，峰值 5.51 ms；实际采样平均间隔 108.52 ms，P95 110.22 ms；读取到渲染回执 P95 4.64 ms，峰值 236.36 ms（包括首次绘制）。轮询 CPU 约占单核 2.44%，按 16 个逻辑处理器总容量粗略归一化约 0.15%。退出回归检查通过，无残留验证进程。

每种系统缩放下各执行 5 次真实测试窗口移动，测量从发出移动命令到对应新边界的渲染回执：

| 系统缩放       | 平均     | 峰值      |
| -------------- | -------- | --------- |
| 100%           | 77.76 ms | 96.35 ms  |
| 125%           | 93.58 ms | 109.69 ms |
| 150%（恢复后） | 82.08 ms | 100.06 ms |

命令通过测试文件传给独立进程，接收端每 50 ms 检查一次，以上包含这部分额外等待以及 100 ms 轮询等待，并不只是 IPC 耗时。

这组 CPU 数据只统计窗口读取，**不是桌宠全部进程的性能验收**。渲染回执是渲染层下一次动画帧返回，不保证屏幕已经呈现。没有测量用户开始拖动到实际屏幕呈现的端到端延迟；不能把 4.64 ms 写成拖动延迟。

## 人工测试发现与修复

用户先后反馈位置错位、移动后消失，以及拖动期间消失。依次定位并修复：画布缺少 CSS 宽高，导致高 DPI 下物理尺寸被再次当作逻辑尺寸显示；逐个 `GetWindow` 遍历在实时换序中出现重复句柄，改为 `EnumWindows` 收集快照；Windows 拖动时活动窗口盖住调试层，改为每次采样调用 `moveTop()`，保持不抢焦点。

修复后，用户确认绿线拖动时正常。画布尺寸和窗口换序已有自动回归检查；拖动时的可见性以这次人工观察为依据。曾尝试用屏幕像素读取验证线条，但结果不可靠，未计入通过项，相关临时探针已移除。六类应用的自绘按钮仍需分别扩展人工覆盖。

## 特殊情况与 M4 建议

1. 工具窗口、最大化窗口不能提供窗口顶边，但必须保留遮挡。自己的调试层按进程 ID 排除；其他软件的透明置顶层仍按矩形处理，可能过度遮挡。
2. DWM 可见边界与 `GetWindowRect` 原点不同。按钮属性使用窗口相对坐标，转换时必须加后者的原点。
3. 部分自绘窗口无法取得有效按钮矩形，目前保守扣掉右侧 160 逻辑像素，并在采样中记录 `buttonsFallback`。该值不是已验证的通用按钮宽度。
4. 有些 DWM 按钮矩形与可见边界差 1 个物理像素，会留下非常短的线段。M4 要按猫的可站立宽度过滤短线段，不能让猫站到这种缝隙中。
5. 当前矩形近似不处理圆角、逐像素透明和悬浮窗；晃动仅按速度检测，可能漏掉一个采样间隔内往返的运动。M4 需要补充事件通知或更高频的运动采样，再决定轮询频率。
6. 退出时最后一条渲染回执可能碰到已销毁窗口，实测发现并补上销毁检查；失败会输出错误并返回非零退出码。需要保持这一回归检查。
7. 在不同 DPI 显示器之间不能直接把绝对屏幕坐标除以单一倍率。当前用 Electron 矩形转换接口，但跨屏行为仍须实测。
