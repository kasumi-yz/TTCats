# 审查 PR

用户让你审查或复查 PR 时，按下面的步骤走。你是审查者：只读和评论。改代码、推送、合并分别留给作者和用户。

## 1. 确认该你审

看 PR 描述里的"作者"，或者关联 issue 上的 `agent:*` 标签。作者必须是另一方：你是 Claude，就只审 Codex 写的；你是 Codex，就只审 Claude 写的。作者是你自己这一方时，停下来告诉用户。

## 2. 读

1. `AGENTS.md`。
2. 关联 issue（PR 描述里 `Closes #` 后面的编号）：`gh issue view <N> --comments`。
3. issue"参考"一节列出的设计方案章节、ADR 和 `CONTEXT.md`。
4. `gh pr view <PR> --comments`、`gh pr diff <PR>`、`gh pr checks <PR>`。

需要在本地跑命令时，把 PR 放进一个临时工作树（`git fetch origin pull/<PR>/head`，再 `git worktree add --detach <仓库外的路径> FETCH_HEAD`），用完删掉。主文件夹一直停在 `main`。

## 3. 检查

每一项都要给出结论：

- **验收标准**：issue 里每一条是否做到；有没有做了 issue 没要求的事。
- **范围**：只改了"允许修改的目录"。动了 `app/src/shared/` 或 `schemas/` 的，对应的接口变更 PR 已经合并。
- **硬性规则**：对照 `AGENTS.md` 的 8 条，逐条检查。
- **依赖**：新增的依赖包在 PR 里列出并说明了原因。
- **测试**：测的是行为，换一个错误的实现就会失败；新功能能在调试台里手动触发。
- **命名**：和 `CONTEXT.md` 一致。
- **正确性**：bug、没考虑到的边界情况、可能弄坏存档的地方。
- **CI 和同步**：CI 通过；PR 没有落后于 `main`，也没有冲突（`gh pr view <PR> --json mergeStateStatus`）。

格式和代码风格交给 lint。

完成标准：每一项都有结论，发现的问题都记下了文件和行号。

## 4. 发意见

用 `gh pr comment` 发一条评论。作者和审查者是同一个 GitHub 账号，approve 会失败，所以用评论代替。

评论第一句写结论：可以合并，或者改完"必须改"以后可以合并。然后按三级列出意见：

- **必须改**：不改不能合并。
- **建议改**：值得改，但不影响合并。
- **可以不管**：小问题。

每条写清文件和行号、问题是什么、建议怎么改。

## 5. 汇报

用中文大白话告诉用户：能不能合并、主要问题是什么。有需要用户拍板的事，按 `AGENTS.md`"和用户沟通"一节，讲清每个选项的影响，并给出你的推荐。

## 一次审多个 PR

依次审：一个 PR 走完第 1～4 步、意见发出去以后，再开始下一个。一次最多审三个。全部审完后，如果这些 PR 改到了相关的地方，在汇报里说明它们之间有没有冲突。

## 复查

作者改完以后：读你上次的评论和作者的回复，逐条确认"必须改"和"建议改"都处理好了，作者没改的理由也站得住；再检查新改动有没有带来新问题。结论照样用 `gh pr comment` 发出去，然后用一句话告诉用户能不能合并。
