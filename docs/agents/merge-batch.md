# 打包合并

用户说"打包合并"（或者点名几个 PR 让你一起合）时，按下面的步骤走。目的是：多个审查通过的 PR，一次解决冲突、只跑一次 CI，用户只点一次合并。

## 1. 挑出要打包的 PR

- 用户点了名的，就用那几个。没点名的，候选是开着、审查结论为"可以合并"（或者符合免审条件）、没有未处理"必须改"的 PR。
- 草稿 PR 只在用户点名时才带上。
- 把清单和每个 PR 的审查状态告诉用户。有还没审过的，说清楚。

## 2. 建合并包分支

在主文件夹 `git pull`，然后：

```bash
git worktree add ../TTCats-batch-<编号们> -b issue-<编号们>-batch origin/main
```

分支名里带上所有关联 issue 的编号，比如 `issue-65-66-67-68-batch`。

## 3. 逐个合进来

- 和 `main` 冲突最少的先合。每合一个就单独提交一次，提交信息写明是哪个 PR、冲突怎么解决的，方便以后按功能回看。
- 解决冲突时，两边的功能都要留下。重点找"两边各写了一份同样的东西"，比如重复的模块、重复的计时器、重复的函数，只留一份，并把所有调用方接到这一份上。
- 不在合并包里加新功能，也不顺手重构。审查意见里留到"同步时处理"的建议改除外。
- `package-lock.json` 冲突时，先合好 `package.json`，再跑 `npm install` 重新生成 lock 文件。

## 4. 验证

`npm ci`、`npm run check`、`npm run build` 全部通过。Windows 冒烟交给 CI。

## 5. 开 PR

- 标题：`合并包：一次合入 #A、#B、#C`。
- 正文写上每个关联 issue 的 `Closes #<N>`，列出合并顺序，并逐条说明冲突怎么解决的。这一节是审查者唯一需要看的地方。
- 推送后，取消原 PR 还在跑的 CI，把排队的电脑让给合并包。
- 在每个原 PR 下留言："已放进合并包 #<编号>，请不要单独合并"。

## 6. 审查

- 只做了机械拼接（两边都保留、去掉明显的重复）：可以免审，告诉用户"冒烟通过就可以合"。
- 删掉或改写了某个 PR 的实现，或者改动了行为：请另一方审查，只看"冲突怎么解决的"那一节。
- 拿不准的时候，把这两种情况的影响讲给用户，让用户决定。

## 7. 合并以后

- 原 PR 会被 GitHub 自动标成"已合并"。草稿 PR 或者没被自动标记的，手动关掉，并留言指向合并包。
- 确认关联 issue 都已关闭。
- 删掉合并包的工作树和各原 PR 的工作树。
- 其余还开着的 PR，这时才需要同步最新的 `main`。
