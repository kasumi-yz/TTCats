# 发版步骤

适用于 Windows 当前用户安装版。正式版本从公开的 `kasumi-yz/TTCats` GitHub Releases 下载更新，不需要登录。开发模式不检查更新。

## 更新在用户电脑上怎么运行

- 开着“自动下载更新”时，启动约一分钟后检查，之后每四小时检查一次。有新版就后台下载，全程不弹窗。
- 下载完成后，设置和调试台显示版本，托盘出现“重启并更新到 x.y.z”。点击后先保存、退出，再静默安装并重启。
- 不点击也会在下一次正常退出时静默安装；这种退出不重新打开程序。
- 关闭自动下载后，不再定时检查；设置和调试台的“检查更新”仍可手动检查并下载。关闭开关不会撤销已经下载好的更新。
- 检查或下载失败显示中文状态、写入日志，下次继续尝试。日志在 `%APPDATA%\TTCats\logs`。
- 本项目没有代码签名，Windows 更新签名验证已关闭。安装包和更新文件通过 GitHub HTTPS 获取，下载仍校验更新清单里的文件校验和。首次安装的 SmartScreen 说明见 [安装说明](安装说明.md)。

## 准备版本

1. 先完成 PR、CI 和 Claude/Codex 交叉审查，由用户合并。一次只合并一个 PR。
2. 在独立工作树的版本准备 PR 中修改 `app/package.json` 的 `version`，用 `npm install --package-lock-only` 同步 `package-lock.json`。当前阶段用 `0.2.x`；不要直接改主目录的 `main`。
3. 验证 `npm ci`、`npm run check`、`npm run build`、`npm run dist`、`npm run test:smoke`，确认版本准备 PR 合并。
4. **AI 必须先征得用户明确同意，才能推版本标签或创建 Release。** 提出要使用的具体版本和用途；“完成 issue”不替代本条同意。删草稿和标签也要先征得同意。

## 推标签并检查草稿

获得同意后，在主目录同步并给已合并的提交打标签（下面的 `0.2.1` 只是例子，要换成实际版本）：

```powershell
git pull --ff-only origin main
git tag v0.2.1
git push origin v0.2.1
```

GitHub Actions 的“草稿发版”工作流只在推 `v*` 标签时运行。标签必须和 `app/package.json` 完全匹配，否则在安装依赖前失败。工作流运行完整检查、Windows 冒烟、打包及内容检查后才创建草稿。

在 GitHub 仓库的 Actions 中等“草稿发版”变绿，再打开 Releases 的草稿：

- 标签和标题是这次版本。
- 有 `TTCats-Setup-x.y.z-x64.exe`、它的 `.blockmap` 和 `latest.yml`。`latest.yml` 中的版本、安装包文件名对应本次版本。
- 不上传 `win-unpacked`、源照片、原始视频、本机模拟文件或测试猫咪包。
- 检查发行说明，说明用户会感受到的变化。

**用户亲自在 GitHub 点“Publish release”后才对外发布。** 草稿不会被正常更新检查发现。普通正式更新使用稳定版本；本机模拟的高版本号不能发布。M2 的两个真实测试版由 #69 单独安排。

重复运行工作流只可更新同一标签的草稿；已发布 Release 会被拒绝覆盖。失败时检查工作流日志，修正后重新准备版本，或对仍是草稿的同一标签重跑。

## 发错了怎么处理

- 还没发布的草稿：征得用户同意后，在 Releases 删除草稿，并删除对应的远端标签（`gh release delete v0.2.1 --cleanup-tag --yes`），再删本地标签（`git tag -d v0.2.1`）。确认草稿和标签都已消失。不要删除别的版本。
- 已发布的错误版本：先通知用户。已经更新到这个版本的电脑不会自动降级；修复后发更高的版本。不要覆写同一个已发布标签和安装包。
- issue #68 的公开试跑只生成草稿、不点发布。试跑与删除都需明确同意，完成后记录工作流链接和资产清单。没有获得同意就把此验收项标为未验证。

## 本机模拟升级

不访问 GitHub Releases、不推标签。安装包使用独立的测试 appId、安装目录、存档目录及缓存，不覆盖正式 TTCats。

在独立工作树根目录执行：

```powershell
npm ci
npm run build
npx tsx app/scripts/simulate-update.ts
```

脚本生成 `0.2.9000` 和 `0.2.9001` 两个仅供本机的 NSIS 安装包，在 `127.0.0.1` 启动更新服务器，然后：静默安装旧版 → 把猫大小设为 1.75 并关闭自动下载 → 手动检查和后台下载 → 普通退出 → 实际运行 NSIS 升级 → 启动新版，核对版本和设置保留。

为了隔离存档，脚本只在测试用的构建输出中注入数据目录，执行结束恢复 `app/out/main/index.js`。正式源码没有安装版测试开关。测试期间不要在同一工作树运行其他构建或启动程序。结果写入脚本打印的临时目录中的 `result.json`；安装包和日志也保留在这个目录里以便核查。

升级必须在两分钟内完成，否则脚本报错；旧版卸载确认若弹出并阻塞，会导致这一步失败。脚本最后静默卸载独立测试应用，不删真实存档。异常时先检查是否有测试应用或安装器仍在运行，再检查输出目录；不要把模拟版本或临时文件提交到仓库。
